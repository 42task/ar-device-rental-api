# 多商户运行说明

共用一套 API 与 admin 管理平台，每个商户独立拥有小程序 AppID、微信支付商户号、支付凭据和 HTTPS 域名。`admin` 表示管理平台，角色为 `root / adminer / manager / user`。本文件说明实现和接入要求，不代表线上迁移、部署、微信上传或正式发布已完成。API 命令在本仓库根目录执行；小程序与独立 admin 的源码、构建和部署分别在各自仓库完成。

## 归属与权限

系统内部 `merchant_id` 表示业务归属，微信 `mchid` 属于支付配置。当前商户继续使用 `d.4mr.cn` 与 `wx03dbf50c15cac06f`；新商户可使用 `d1.4mr.cn` 等独立域名。

| 操作 | 规则 |
| --- | --- |
| root 创建/编辑商户 | 在 admin「商户管理」维护名称、编号、域名、小程序、支付和状态 |
| root 切换商户 | 顶栏显示当前商户；业务请求带 `X-Merchant-Id`，服务端核验 root |
| adminer / manager / user | 一次归属一个商户，权限只对本商户生效 |
| adminer 管理人员 | 沿用既有层级，只能调整本商户其他 user / manager |
| adminer / manager 新增设备 | 后端采用操作者所属商户，不接受任意商户编号 |
| 新用户扫码 | 在设备所属商户的小程序登录，设备真实归属由后端核验 |
| 已有账号扫描其他商户设备 | 提示商户不一致，扫码不自动迁移身份或权限 |

默认商户现有用户、设备 UUID、订单编号、费用、押金、状态、手机号绑定和角色保持原业务含义。保留 `/api/v2`、二维码 `https://d.4mr.cn/d?i=UUID&t=TYPE`、型号映射、整数分金额、定价版本、设备占用、验签和退款机制。迁移归入默认商户，不重建订单或重置支付。旧参数 `uuid/type`、旧域名和 HTTP 码仍不兼容。

## 商户配置与状态

每个商户分别保存 AppSecret、商户私钥、API v3 密钥、证书序列号与微信验签配置。admin 只显示配置是否存在及支付就绪状态；敏感字段不回填，编辑留空表示保留原值。凭据只在服务端加密存储，不进入小程序、静态文件、Git、日志或镜像。

- `draft`：待配置，root 可在平台配置；已有身份可处理历史业务，暂不接受新注册、调入或新租赁。
- `active`：已启用，配置和设备满足条件时接受新租赁。
- `paused`：暂停新租赁，历史回调、查单、退款继续处理。

支付开放开关与配置完整性分别判断。配置变更保留历史版本，订单固定原商户、原收款账户及配置引用。已有业务不直接替换 AppID 或域名。一个商户支付未就绪仅影响该商户，不代表整个 API 失效。

同一收款账户轮换凭据时，registry 选该账户最新有效签名凭据，并合并对应验签公钥；回调仍保留原 `configId` 地址。延迟通知先验签，再最多尝试 8 把不同的 API v3 密钥，包含原配置密钥；同一密钥的多次配置编辑不应挤掉原密钥。更换 `mchid` 后，旧订单仍使用原 `mchid` 查单和退款，不能跟随新收款账户。

新增敏感配置加密使用 `MERCHANT_CONFIG_KEY` 或 `MERCHANT_CONFIG_KEY_PATH`，为 32 字节密钥，支持 64 位十六进制或 Base64。建议放在原只读 secrets 目录的 `merchant-config-key` 文件，默认路径 `/run/secrets/merchant-config-key`。应妥善备份，不能随意替换或删除，否则无法解密已有商户配置。默认商户继续沿用现有环境配置，未设置新加密密钥时其原业务仍可运行。

## 设备与人员调拨

设备「调拨」仅 root 可用，要求无进行中的租赁、待确认支付、占用或未完成退款。事务内调整归属后，设备暂停开放并增加配置版本；目标商户换贴自身域名二维码、核对费用后重新开放。设备 UUID 与历史订单不变，旧订单和退款保留原商户及配置。

用户「分配商户」仅 root 可用，需指定目标商户、角色和原因。先生成有期限的一次性绑定，admin 当前弹窗向操作者展示目标小程序及凭据，不写浏览器存储或日志。仅交给目标用户本人。

用户在原商户小程序首页进入「确认商户分配」，填写凭据并主动确认。前端先用原账号 Bearer 调用 `POST /api/v2/rental/auth/merchant-binding/confirm`，服务端核对被分配账号、原商户及邀请后记录源确认；只有成功才按服务端返回的 AppID 打开目标 `pages/merchant/bind?bindToken=...`。目标再核对商户并确认，登录接口要求邀请已源确认。root 不能替代原账号完成该步骤。

目标绑定页在确认前不自动登录，避免先建立另一账号而冲突。服务端用目标 AppID 的真实微信登录代码完成绑定，不修改或混用跨小程序 OpenID，不按手机号自动合并。该机制验证源账号参与与目标真实微信登录，不声称自动识别跨 AppID 的同一微信。若目标身份已被另一账号使用，明确报冲突，由 root 核对处理。凭据使用后失效。旧会话失去原商户管理权限，历史订单与资金记录仍归原商户；目标商户管理登录仍需独立手机号授权。

## 小程序构建

小程序仓库 `ar-device-rental-mp` 使用同一份源码生成各商户独立上传目录，源码保留默认商户配置。各商户分别配置微信 request 合法域名、普通码规则、体验成员，并分别上传、审核和发布。普通二维码只匹配当前商户包的配置域名，保持 `i/t` 格式；设备真实归属以服务端为准，商户不一致时明确提示，不自动跨小程序传递令牌。

公开构建清单仅允许 `code / name / appId / origin`，不得包含密钥。例如：

```json
{
  "code": "merchant2",
  "name": "第二商户",
  "appId": "wx1111111111111111",
  "origin": "https://d1.4mr.cn"
}
```

AppID 是示例，须替换为目标商户真实值。以下命令在小程序仓库根目录执行，输出必须是源项目之外尚不存在的独立目录：

```sh
npm run prepare-merchant -- --manifest /绝对路径/merchant2.json --output /绝对路径/merchant2-miniprogram
node scripts/validate-upload.js --project-dir /绝对路径/merchant2-miniprogram
```

只复制白名单源码与公开配置，不复制微信私有配置、测试数据或凭据。校验会核对商户清单、项目 AppID、API/二维码域名和页面文件，保留防止误传商户的保护。开发者工具只导入目标生成项目目录，不导入工程根目录。

## 域名与部署

独立仓库 `ar-device-rental-admin` 提供线上管理平台，本仓库 `admin/` 是同内容静态副本；两份资源保持同步。线上 `/admin/` 由独立 NGINX 服务提供，其余 API 请求仍去后端，不开放跨域。独立仓库的提交、CI、镜像和部署分别核实。

本仓库及独立 admin 的 Compose 共用 `RENTAL_HOST_RULE`，默认仍为当前商户。增加第二域名时在受控部署环境使用同一规则：

```text
Host(`d.4mr.cn`) || Host(`d1.4mr.cn`)
```

admin 额外匹配 `/admin` 与 `/admin/` 前缀并保留更高路由优先级。保留原数据库卷、网络和支付密钥挂载。admin 创建商户只新增业务配置，DNS、HTTPS、Traefik 和微信后台仍需接通后才能使用。

微信域名验证文件按商户分别配置。既有微信域名验证服务的精确路由保持原状；新商户添加自己的域名和精确文件路径，不覆盖已有文件、API、admin 或回调。

后端仅信任受控代理并按登记域名解析商户。未知域名不回退默认商户。Cookie 保持 host-only、HttpOnly、Secure、SameSite=Strict；写接口校验对应 Origin，不共享 `.4mr.cn` Cookie。

## 验收与上线

本仓库执行 `npm test`、`npm run build`；独立后台在其仓库执行 `npm test`。事务、并发和退款在专用本机测试实例执行 `npm run test:integration`，不使用生产数据或真实扣款退款。

先做默认商户迁移回归，再验证第二测试商户：跨商户枚举、伪造 header、错误域名/Origin/AppID、root 商户管理、adminer/manager 新增归属、密钥不回显、设备占用禁调、调拨换码与费用版本、一次性绑定和旧会话失权、支付失败/重试/并发/重复回调、退款未完成保持占用。商户暂停、换配置或人员设备调拨后，原订单仍使用原支付配置。

合并、CI、镜像、Portainer、微信上传、体验版、审核和正式发布分别记录。回滚要协调数据库版本，出现新商户业务数据后不能直接切回仅识别单商户的旧应用。
